# Automated Multi-Platform Posting

A FastAPI application that publishes one short message through five real third-party APIs: **Mastodon, Bluesky, Telegram, Discord, and Slack**. Platforms are selected internally; the caller submits only a message. Requests run concurrently, and a failure on one platform does not stop the others.

**Verification status:** automated tests use mocked HTTP responses. No live credentials were provided, so live posting and anonymous public availability have not been verified. The application has no simulated-success mode. Missing credentials return explicit failures. The separate offline demonstration labels every fixture as simulated.

## Quick start

Requires Python 3.11 or newer. Verified locally with Python 3.14.3.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
# Fill in your platform credentials in .env, then start:
uvicorn app.main:app --host 0.0.0.0 --port 4000
```

On Windows, activate with `.venv\Scripts\activate`. Restart the server after changing `.env`.

- Swagger documentation: <http://localhost:4000/docs>
- OpenAPI schema: <http://localhost:4000/openapi.json>
- Posting endpoint: `POST http://localhost:4000/posting`

This is a local assessment server. Its posting endpoint has no authentication; keep it local. An Internet deployment would need caller authentication and rate limits before exposing your posting credentials.

## Request

```bash
curl -sS -X POST http://localhost:4000/posting \
  -H 'Content-Type: application/json' \
  -d '{"message":"Explore our latest business platform: https://example.com"}'
```

Validation returns **HTTP 422**, before any platform call, for:

- Empty, non-string, or more than 200-character messages.
- Missing or multiple CTA links, including punctuation-adjacent links.
- Invalid URL hostnames, malformed authorities, ports or percent escapes.
- Schemes other than HTTP/HTTPS, schemeless URLs, or credentials inside URLs.
- Additional body properties such as `platforms`.

The 200-character limit counts Python Unicode code points, including whitespace and the URL; the message is preserved. A CTA must be explicit HTTP(S). Bare domains outside it are treated as additional links. Terminal sentence punctuation and unmatched closing parentheses are excluded from the CTA facet. Encode a nested URL in a query parameter (for example `https%3A%2F%2Fexample.org`); multiple unencoded `://` sequences are rejected. Validation checks syntax only: it does not fetch the CTA or guarantee the target exists.

## Response semantics

Every valid request returns **HTTP 200** with five results in a fixed order. Inspect `success` and each result; HTTP 200 alone does not mean publication succeeded.

| Field | Meaning |
| --- | --- |
| `success` | At least one platform confirmed publication. False if all failed. |
| `platform` | Internally selected platform name. |
| `status` | `success` or `failed`. |
| `posted_url` | Actual returned permalink, or one constructed from confirmed identifiers. Null when no permalink is available. |
| `public_access` | Expected anonymous access based on platform visibility metadata; not an independent browser verification. |
| `date`, `time` | Publication date and time in **UTC**, null for failures. |
| `error` | Safe failure details; also used for a metadata warning after a confirmed post. Otherwise null. |

A confirmed Slack post remains successful if its subsequent permalink lookup fails; its URL is null and its error explains the warning. Telegram direct chats can also succeed without a permalink. Timeouts indicate an unknown outcome because the remote service may have accepted the post. No automatic retries occur, and repeating the request can create duplicate posts.

With no credentials, an **actual** response is:

```json
{
  "success": false,
  "results": [
    {"platform":"Mastodon","status":"failed","posted_url":null,"public_access":false,"date":null,"time":null,"error":"Not configured: MASTODON_ACCESS_TOKEN"},
    {"platform":"Bluesky","status":"failed","posted_url":null,"public_access":false,"date":null,"time":null,"error":"Not configured: BLUESKY_IDENTIFIER, BLUESKY_APP_PASSWORD"},
    {"platform":"Telegram","status":"failed","posted_url":null,"public_access":false,"date":null,"time":null,"error":"Not configured: TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID"},
    {"platform":"Discord","status":"failed","posted_url":null,"public_access":false,"date":null,"time":null,"error":"Not configured: DISCORD_WEBHOOK_URL, DISCORD_GUILD_ID"},
    {"platform":"Slack","status":"failed","posted_url":null,"public_access":false,"date":null,"time":null,"error":"Not configured: SLACK_BOT_TOKEN, SLACK_CHANNEL_ID"}
  ]
}
```

Successful and partial-success response examples are generated by [the offline demonstration](scripts/offline_demo.py) and saved in [evidence/offline-demo.json](evidence/offline-demo.json). Those examples are **fixtures, not evidence of live publishing**.

## Platform research and credentials

Detailed research, authentication requirements, endpoints, and official documentation are in [docs/PLATFORMS.md](docs/PLATFORMS.md).

| Platform | Local configuration | Expected public access |
| --- | --- | --- |
| Mastodon | Instance origin + user access token with `write:statuses` | True for returned public/unlisted visibility. |
| Bluesky | Actual account PDS, identifier, app password | Public feed record; client moderation/account settings may affect visibility. |
| Telegram | BotFather bot token + channel ID; grant bot channel posting rights | True only for a returned public channel with a username. |
| Discord | Standard text-channel webhook URL + numeric server ID | False; the message link requires Discord/channel access. |
| Slack | Bot token with `chat:write` + channel ID; invite bot to channel | False; workspace/channel access is required. |

All five are supported publishing destinations. Slack and Discord are intentionally reported as non-public; a channel named “public” is not the same as anonymous web access. LLM completion endpoints are not selected because generating text does not publish a publicly addressable post.

Configure all five for a complete live demonstration. Missing credentials or an API authentication failure affect only that platform. Malformed platform origins or webhook URL formats are rejected at startup as configuration errors. Never commit `.env`, tokens or webhook URLs. Upstream response bodies, exception values and HTTPX URL logs are not forwarded because they can contain credentials.

### Capture live proof before submission

1. Configure credentials for accounts/channels you control, then run the server.
2. Send a single meaningful test message with one link. This creates real posts on all configured platforms.
3. Save the response locally: append `-o evidence/live-response-local.json` to the curl command. This file is ignored by Git until reviewed.
4. Open each returned URL. Check public links while logged out; Slack/Discord will require channel access. Capture redacted Swagger screenshots or reviewed logs as `evidence/live-proof.*` and add them to your repository.
5. Check for secrets and personal information before publishing. Never label offline fixture URLs as live posts.

No platform accounts were created and no external messages were posted during preparation.

## Structure and decisions

```text
app/
  main.py                  # FastAPI app, lifespan and shared HTTPX client
  config.py                # Environment configuration with secret fields
  schemas.py               # Request validation and response contract
  platforms/               # Five independent real API adapters + base helpers
  services/posting_service.py # Concurrent fan-out and isolated outcomes
tests/                     # Offline integration/validation/error tests
scripts/offline_demo.py     # Explicitly mocked demonstration, separate from server
docs/PLATFORMS.md           # API research and account setup
evidence/                  # Actual checks and labeled fixture outputs
```

The scope is synchronous fan-out for a short assessment: no database, queue, retries, distributed idempotency, or persistent Bluesky sessions. Bluesky signs in for each request, which is subject to its login rate limits. Each HTTP operation has a configurable timeout; a multi-step adapter can take more than one timeout interval. In a production system, use durable job state, idempotency, session refresh and controlled retries.
